## Task A4: HTTP for Embedded Control — Protocol Reflection

# a)

HTTP ist ein zustandsloses Request-Response-Protokoll. Jede Anfrage ist unabhängig, und der Server merkt sich nicht automatisch vorherige Anfragen. Für das Schalten einer LED ist das einfach und ausreichend, aber nicht ideal für echte Echtzeitsteuerung, da jede Aktion eine neue HTTP-Anfrage benötigt.

Bei zwei Wemos D1 Minis im gleichen WLAN würden wir die Round-Trip-Time auf etwa **10–100 ms** schätzen (haben nicht genau gemessen). Für eine LED ist das schnell genug, aber für Motorsteuerung, Robotik oder sicherheitskritische Regelungen wäre HTTP zu langsam und zu unzuverlässig.

# b) 
MQTT funktioniert anders: Es nutzt ein Publish-Subscribe-Modell. Ein Client veröffentlicht zum Beispiel `led/toggle` auf ein Topic, und der LED-Controller abonniert dieses Topic. Ein Broker verteilt die Nachrichten. Dadurch skaliert MQTT besser, besonders bei mehreren Clients. Bei 10 Clients ist MQTT sauberer als HTTP, weil nicht jeder Client direkt den Server ansprechen muss.

# c)
HTTP ist also gut genug für einfache CPS-Aufgaben wie LED-Schalten oder gelegentliches Senden von Sensordaten. Für schnelle oder kritische Systeme braucht man effizientere Protokolle wie MQTT, UDP, WebSockets oder Echtzeitprotokolle.
